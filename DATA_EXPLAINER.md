# MacroFit Data Explainer

## Purpose

The data supports a reproducible prototype of meal planning under budget, nutrition, dietary, and meal-slot constraints. It is synthetic data created to test the system pipeline. It is not a record of current outlet prices and is not medically verified nutrition data.

## Files and join

`data/menu.json` contains 60 menu items across 10 synthetic outlets. `data/nutrition.json` contains one nutrition record for each menu item. Python joins the two files using `item_id`. The loader stops when a menu item has no nutrition row, a nutrition row has no menu item, or an identifier is duplicated.

`data/meal_rules.json` defines the three daily meal slots, suggested times, the light-breakfast allowlist, the 500 kcal breakfast ceiling, and items excluded from lunch and dinner.

## Menu fields

| Field | Meaning |
|---|---|
| `item_id` | Stable join key such as `H01` |
| `shop` | Synthetic outlet name |
| `item` | Human-readable food name |
| `cuisine` | Cuisine label used for subjective comparison |
| `price_sgd` | Synthetic price for one listed serving |
| `dietary_type` | `vegetarian`, `egg`, `chicken`, `fish`, or `beef` |
| `spice_level` | Mild, medium, or spicy preference label |
| `heaviness` | Light, balanced, or hearty preference label |
| `meal_format` | Rice or bowl, noodles, handheld, salad, soupy, or breakfast cup |
| `portable` | Whether the item is suitable for carrying |
| `preference_tags` | Searchable descriptors supplied to the preference layer |
| `preference_metadata_status` | States that preference labels are synthetic and rule-annotated |

The current category counts are 20 chicken, 19 vegetarian, 11 fish, 5 egg, and 5 beef items. MacroFit defines vegetarian as containing no meat, fish, or egg. Dairy may still be present. The project does not certify allergens.

## Nutrition fields

Each nutrition row records calories, protein, carbohydrates, fat, fibre, and sodium for one listed serving. The row also records `source_family`, `source_match`, `mapping_method`, `mapped_by`, `mapped_on`, and `confidence` so that uncertain matches remain visible.

The 60 mappings contain 8 high-confidence, 36 medium-confidence, and 16 low-confidence rows. Source-family labels include USDA FoodData Central and Singapore HealthHub. They describe the reference family used for the synthetic match; they do not mean the final values were independently verified by those organisations.

## Construction method

Nagur Pavan created the mappings using a generic dish match, component match, nearest dish match, or portion scaling. For example, a dish may be represented by a generic prepared-food record, or by adding its main components and scaling them to the intended serving. This method is sufficient to exercise joins, arithmetic, constraints, and evaluation. It is not sufficient for medical use or a public product.

## Validation performed by code

The loader checks item coverage and identifier consistency. Tests confirm 60 joined items across 10 outlets. The optimizer recomputes every plan total from trusted dataset rows and quantities. It does not accept calories, macros, or prices generated by the language model. Unknown item IDs are rejected.

The meal planner also verifies meal-slot suitability, prevents the same item from appearing twice in one day, excludes items already recommended during the active session, and applies a penalty to recently eaten items when that history is available.

## Known data risks

The main risk is a plausible but incorrect match. A wrong dietary label or nutrition mapping can silently pass through correct code. Egg Fried Rice was initially labelled vegetarian, showing why category definitions matter. Egg dishes now use their own category. Yong Tau Foo item H04 still requires review because its generic nutrition match refers to fishcake while its menu label is vegetarian.

Other limitations include synthetic prices, subjective preference labels, generic portion assumptions, and the absence of independently verified allergy data. Session history is held in memory and is lost when the Colab runtime restarts.

The dataset records dietary type, spice level, heaviness, meal format, portability, and cuisine. It does not say whether a dish is served warm, feels comforting, or is familiar to a particular person. The project therefore does not treat those qualities as verified facts. The model may consider them while comparing options, but Python cannot guarantee them from the current data.

## Requirements for a real pilot

Before real use, prices should be collected with timestamps, portions should be measured, nutrition should be reviewed by a qualified person, and every dietary and allergen label should be verified with the outlet. Changes should preserve the stable `item_id`, mapping method, source, date, and confidence fields so revisions remain auditable.
